# دستیار ترمینال لینوکس — LTA

این نسخه علاوه بر تولید دستور، می‌تواند مسئله را به مراحل وابسته تقسیم کند،
تغییرات را پیش از اجرا نشان دهد، خروجی مراحل را ثبت کند و نتیجه را با معیار
مشخص بررسی کند. هسته فقط از کتابخانهٔ استاندارد پایتون استفاده می‌کند.

## نصب و شروع

پایتون ۳٫۸ یا جدیدتر لازم است. اجرای Bash و مدیریت سرویس برای لینوکس است؛
در ویندوز از یک نشست لینوکسی WSL استفاده کنید. ابزارهای فایل و برنامه‌ریزی
در ویندوز نیز قابل استفاده‌اند. ابزارهای Git، Docker، Nginx و systemd باید
برای مهارت مربوطه روی سیستم موجود باشند.

```bash
./install.sh
lta -p rule_based -d "فضای دیسک"
lta config set provider ollama
lta config set ollama.model qwen2.5-coder:7b
lta --agent -p ollama "تنظیمات این پروژه را بررسی و مشکل را اصلاح کن"
lta --agent --adaptive --max-rounds 3 -p ollama "علت بالا نیامدن سایت محلی را پیدا کن"
```

حالت `--agent` یک طرح مرحله‌ای می‌سازد. حالت `--adaptive` پس از اجرای طرح،
شواهد را به مدل برمی‌گرداند تا نتیجه را تحلیل یا طرح بعدی را پیشنهاد کند.
تعداد دورها و فراخوانی‌های مدل محدود است. با `-d` فقط طرح و تغییرات پیشنهادی
را می‌بینید؛ ممکن است فرادادهٔ جلسه ذخیره شود ولی ابزار اجرایی اجرا نمی‌شود.

## ایمنی و تأیید

- `-y` فقط عملیات خواندنیِ شناخته‌شده را بدون سؤال اجرا می‌کند.
- دستور ناشناخته یا ترکیبی، تغییر فایل و تغییر سرویس نیاز به تأیید دارند.
- Enter به‌تنهایی تأیید نیست. ویرایش دستور باعث بررسی مجدد آن می‌شود.
- قبل از تغییر فایل، اختلاف نسخه‌ها نمایش داده و نسخهٔ پشتیبان محلی ثبت می‌شود.
- ابزار فایل فقط داخل پروژه کار می‌کند و مسیرهای حساس و symlink را رد می‌کند.
- بازگردانی، تغییر جدیدتر کاربر را بازنویسی نمی‌کند.
- شکست یک مرحله یا بررسی نتیجه، اجرای مراحل بعدی را متوقف می‌کند.
- Ctrl+C و مهلت اجرا، فرایند در حال اجرا را متوقف می‌کنند؛ در لینوکس گروه
  فرایند نیز متوقف می‌شود.

این سیاست‌ها جایگزین sandbox نیستند. Bash پس از تأیید با دسترسی حساب شما
اجرا می‌شود. حذف اطلاعات محرمانه نیز بهترین تلاش بر اساس الگوها و کلیدهای
شناخته‌شده است و تضمین شناسایی همهٔ اسرار نیست.

دستورها ورودی تعاملی ندارند؛ ویرایشگر تمام‌صفحه و ورود رمز را در ترمینال جدا
انجام دهید. برای تغییر سرویس با sudo، احراز هویت را از قبل انجام دهید.

## عیب‌یابی سرویس و مهارت‌ها

```bash
lta doctor nginx --url http://127.0.0.1/health
lta doctor nginx --repair --url http://127.0.0.1/health
lta skills list
lta skills run git -y
lta skills run network -d
lta skills run systemd --service ssh
lta skills install examples/config-repair.skill.json
```

مهارت‌های آماده شامل Git، Docker، شبکه، systemd و Nginx هستند. گزینهٔ
`--repair` در doctor راه‌اندازی مجدد را پیشنهاد می‌کند؛ اصلاح همهٔ علت‌ها را
تضمین نمی‌کند. برای Nginx، اعتبارسنجی تنظیمات باید پیش از restart موفق باشد.
پس از آن وضعیت سرویس و در صورت ارائهٔ URL پاسخ HTTP بررسی می‌شود.

مهارت نصب‌شدنی یک فایل JSON معتبر است؛ نصب آن هیچ دستوری اجرا نمی‌کند.
طرح‌ها هنگام اجرا همچنان از تمام کنترل‌ها و تأییدها عبور می‌کنند.
ویرایش خودکار فایل‌های خارج پروژه، مانند `/etc`، در ابزار فایل مجاز نیست.

برای پایش زندهٔ نرخ دریافت و ارسال شبکه، بدون نصب ابزار اضافی:

```bash
lta skills run traffic -y
```

این ابزار شمارنده‌های رابط‌های لینوکس را ده ثانیه نمونه‌برداری می‌کند و نرخ‌ها
را بر حسب KiB/s نشان می‌دهد. محتوای بسته‌ها را نمی‌خواند. مدت نمونه‌برداری
در طرح JSON از یک تا شصت ثانیه قابل تنظیم است و نباید از timeout بیشتر باشد.
در حالت مسیریابی ساده، درخواست دقیق `Monitors live network traffic` نیز از
همین ابزار استفاده می‌کند؛ درخواست‌های ترکیبی همچنان به مدل می‌روند.

برای جلوگیری از خطاهای قالب خروجی مدل‌های کوچک، درخواست برنامه‌ریزی Ollama
همراه JSON Schema ارسال می‌شود. شناسهٔ مرحلهٔ نامعتبر فقط در صورت بی‌ابهام بودن
وابستگی‌ها اصلاح می‌شود. وابستگی مبهم یا رو به جلو رد می‌شود. خروجی نامعتبر
مدل حداکثر یک فرصت اصلاح دارد و این فراخوانی در محدودیت مصرف حساب می‌شود.
طرح واردشده توسط کاربر همچنان باید قالب معتبر داشته باشد.

## حافظه و ادامهٔ کار

```bash
lta sessions
lta sessions latest
lta resume
lta resume --retry
lta resume --replan -p ollama
lta export-plan plan.json
lta run-plan plan.json -d
lta run-plan plan.json
lta rollback BACKUP_ID
```

حافظهٔ هر پروژه جداست. برای انتخاب پروژه از `--project /path/to/project`
استفاده کنید. مراحل موفق دوباره اجرا نمی‌شوند. مرحلهٔ نیمه‌تمام یا ناموفق
فقط با درخواست صریح `--retry` تکرار می‌شود. `--replan` با استفاده از شواهد
ذخیره‌شده طرح تازه می‌سازد. قفل اجرای پروژه از اجرای هم‌زمان دو طرح جلوگیری
می‌کند. ابزار `change_directory` مسیر جاری را بین مراحل نگه می‌دارد.

جلسه‌ها و نسخه‌های پشتیبان در مسیر دادهٔ کاربر قرار می‌گیرند:
`~/.local/share/linux-terminal-agent/projects/` یا مسیر تعیین‌شده با
`XDG_DATA_HOME`. تاریخچهٔ سراسری نسخهٔ قبلی به‌طور خودکار وارد پروژه‌ها نمی‌شود.

## مدل، حریم خصوصی و هزینه

```bash
lta config set local_only true
lta config set timeout 60
lta config set max_steps 12
lta config set max_model_calls 20
lta config set route_simple false
lta --agent --local-only -p ollama "پروژه را بررسی کن"
```

حالت محلی، مدل ابری و endpoint غیر loopback را رد می‌کند. انتقال خودکار به
ابر وجود ندارد. درخواست‌های مدل محلی از proxy محیط استفاده نمی‌کنند و redirect
را دنبال نمی‌کنند. این محدودیت مربوط به مدل است؛ firewall برای دستور Bash یا
ابزار HTTP نیست.

مدیریت خطای موقت برای همهٔ مدل‌های آنلاین یکسان است و مدل یا سرویس انتخاب‌شده
تغییر نمی‌کند. پیش‌فرض چهار تلاش مجدد در بازهٔ ۱۲۰ ثانیه است؛ timeout هر درخواست
به زمان باقی‌مانده محدود می‌شود. انتظار بیش از ۶۰ ثانیه، خطای قابل‌اقدام می‌دهد
و درخواست زودتر از زمان اعلام‌شدهٔ سرویس ارسال نمی‌شود.

برای 503 فاصله از حدود دو ثانیه شروع و دوبرابر می‌شود؛ برای 429 حداقل ده ثانیه
است. زمان طولانی‌تر در هدر Retry-After یا RetryInfo بدنهٔ Gemini رعایت می‌شود.
اتمام سهمیهٔ روزانه، سهمیهٔ صفر و اتمام اعتبار، با تلاش مجدد بیهوده تکرار نمی‌شوند.
خطاهای دسترسی، درخواست نامعتبر و گواهی TLS نیز تکرار نمی‌شوند. هر فراخوانی واقعی
در محدودیت تعداد و بودجه محاسبه می‌شود.

زمان توقف در مسیر دادهٔ کاربر ذخیره می‌شود و با بستن REPL یا اجرای دوبارهٔ CLI
از بین نمی‌رود. کلید API ذخیره نمی‌شود؛ نام فایل از هش اعتبارنامه، endpoint و
مدل ساخته می‌شود. پس از پایان تلاش‌های موقت، حداقل ۳۰ ثانیه توقف برقرار است؛
برای اتمام سهمیه حداقل پنج دقیقه یا زمان طولانی‌تر اعلام‌شدهٔ سرویس.
این سازوکار ظرفیت سرویس یا سهمیهٔ حساب را افزایش نمی‌دهد؛
[راهنمای رسمی Google](https://ai.google.dev/gemini-api/docs/troubleshooting)
تفاوت خطای موقت و نیاز به اصلاح حساب را توضیح می‌دهد.

```bash
lta config set max_retries 4
lta config set gemini.max_retries 4
lta config set retry_deadline 120
lta config set retry_max_wait 60
lta config set provider_cooldown true
```

مقدار تلاش مجدد صفر تا پنج است و تنظیم اختصاصی سرویس اولویت دارد. تنظیمات
قدیمی شما حفظ می‌شوند؛ برای Gemini مقدار ذخیره‌شدهٔ قبلی را صریحاً تغییر دهید.
پس از رفع مشکل حساب، تنظیم `provider_cooldown false` اجازهٔ نادیده گرفتن توقف
ذخیره‌شده را می‌دهد؛ سپس آن را دوباره true کنید. پس از تغییر تنظیمات REPL را
دوباره اجرا کنید. درخواست دقیق `show open ports` با فعال بودن
`route_simple` بدون مدل ابری پردازش می‌شود. پس از تغییر تنظیمات، از REPL
خارج شوید و دوباره آن را اجرا کنید.

مدل هر سرویس جداگانه قابل تنظیم است. `-m` اولویت دارد؛ مقدار قدیمی `model`
در سطح اصلی فقط برای سرویس پیش‌فرض اعمال می‌شود. برای استفاده از مدل اختصاصی
هر سرویس، آن را خالی کنید. نام مدل‌های پیش‌فرض نمونه‌اند و باید با سرویس واقعی
شما سازگار باشند.

پیش‌فرض Gemini اکنون `gemini-3.8-flash` و پیش‌فرض Claude برابر
`claude-sonnet-4-6` است؛ این نام‌ها با مستندات رسمی
[Google](https://ai.google.dev/gemini-api/docs/models) و
[Anthropic](https://platform.claude.com/docs/en/about-claude/model-deprecations)
بررسی شده‌اند. تنظیمات ذخیره‌شدهٔ شما حفظ می‌شوند؛ مدل قدیمی را با
`lta config set gemini.model gemini-3.8-flash` یا تنظیم `anthropic.model`
تغییر دهید.

فرمان `resume` در محیط تعاملی، حالت dry-run و تنظیمات جاری را حفظ می‌کند.
Ctrl+C اجرای گردش کار را متوقف می‌کند و مرحلهٔ قطع‌شده در جلسه ثبت می‌شود؛
ادامهٔ آن نیاز به `--retry` یا `--replan` صریح دارد. محدودیت فایل بر اساس
بایت UTF-8 محاسبه می‌شود تا فایل‌های فارسی نیز قابل خواندن و بازگردانی بمانند.

توکن‌های گزارش‌شده، زمان پاسخ و تعداد فراخوانی‌ها نمایش داده می‌شوند. هزینه
فقط با نرخ واردشدهٔ شما محاسبه می‌شود و موارد نامعلوم مشخص می‌مانند. تنظیم
`pricing` شامل نام `provider/model` و نرخ‌های `input` و `output` به دلار برای
یک میلیون توکن است. `budget_usd` یک محدودیت تخمینی با رزرو هزینهٔ فراخوانی
بعدی است، نه تضمین مبلغ صورتحساب. اگر نرخ مدل ابری مشخص نباشد، اجرای دارای
بودجه رد می‌شود. اطلاعات مصرف در جلسه‌های چندمرحله‌ای ذخیره می‌شود.

## رابط و آزمون

با `lta` وارد محیط تعاملی شوید. فرمان‌های `agent <goal>`، `sessions`،
`resume`، `cd <directory>`، `history`، `help` و `exit` موجودند. نمایش مراحل،
اختلاف فایل و خروجی زنده در ترمینال انجام می‌شود. این رابط خط‌محور است؛ نمایش
راست‌به‌چپ فارسی به قابلیت ترمینال بستگی دارد.

```bash
python -B -m unittest discover -s tests
lta evaluate
lta evaluate --output evaluation.json
```

آزمون‌ها سیاست اجرا، حفظ حریم خصوصی، هزینه، ادامهٔ جلسه، بررسی نتیجه، بازگردانی،
حلقهٔ تطبیقی، HTTP محلی و توقف فرایند را پوشش می‌دهند. ارزیاب سناریوهای محلی
و موقت اجرا می‌کند و کیفیت استدلال مدل‌های واقعی یا سرویس systemd میزبان را
اندازه‌گیری نمی‌کند. روش اجرای تست در کانتینر و قالب JSON در راهنمای انگلیسی
و `docs/PLAN_SCHEMA.md` آمده است.
